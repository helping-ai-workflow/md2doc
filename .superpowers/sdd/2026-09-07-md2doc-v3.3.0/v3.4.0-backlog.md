# v3.3.0 執行過程中量測出來、沒有在本版收掉的項目

這份檔案分成**三**類，而且分類本身是有意義的，不是排版：

- **裁定延後的缺陷** —— 是缺陷，有人會去修，修完就不見了。
- **已知且刻意接受的邊界** —— 不是缺陷，將來也還會在那裡；沒有「修好」這個終點。
- **未裁定的開放問題** —— 既沒被證明是缺陷，也沒被接受成邊界。

「每一項都被驅動量測過」這句話**只對前兩類的多數成立，不是全部**：
下面凡是沒有被實際驅動出來的，都在該項自己的文字裡講明白。

## 一、裁定延後的缺陷

### 資料會被弄髒的（優先）

   （Ruling T5-6b）在 `1d1f0a6` 上逐位元組重現，既存缺陷。與 F10 不同根因（F10 是吞噬

   放大了一個資料缺陷的曝光面** —— 這件事本身沒有被任何 per-task review 看見。

   檔案、不同修法**；刻意不釘測試 —— **斷言今天這組錯的位元組，會讓將來真正的修法

## 二、已知且刻意接受的邊界

**這一區不是工作清單。** 這些項目沒有「修好」的終點：它們是設計極限、瀏覽器行為、
或本版刻意畫出的範圍線。把它們跟上面那一區混在一起，會讓讀的人以為有十九件事在排隊。

14. **F10 的吞噬信號有兩個已量測的沉默缺口**：新 opener 與既有 closer 配對而使文件
    well-formed 的三個落點（與使用者刻意「轉換成程式碼」**在結果上同形**）；以及
    「刪掉 closer 並同時刪掉被吸收行內容的另一份副本」（佔真吞噬的 2.0–9.2%）。
    **誤報方向量測乾淨**（24,411 個非吞噬手勢、0 個內容可辨的誤報）。（T5-8 / T5-13）

15. **F10 有一個內在的誤報**：trim-to-EOF 且把被剪掉那行複製進 fence 內 —— 那兩個手勢
    產生**逐位元組相同的文件**，**任何以文件為輸入的謂詞都不可能分開它們**。是設計
    極限，不是未修的缺陷。

16. **N4 的降級路徑（`unlocatable`）在真實語料上不可達** —— 35k 合成形狀 + 131 個真實
    序列化字串 + 1231 個突變，`at < 0` 一次都沒觸發。機制以擾動 `marked.lexer` 的方式
    驗過。

17. **按下的起點若落在既有選取範圍內，Chromium 走的是拖曳文字手勢** —— 只有
    `dragstart` / `dragend`，沒有 `selectionchange`，Tab 選格造成的浮動格式列抑制
    因此沒有東西可以解除它。以 ablation 證實拿掉本版的抑制邏輯一樣會發生，所以是
    瀏覽器行為而非本版殘留。

18. **點進 fenced code block，caret 一律落在第 2 行，不管你點的是哪一行。**
    v3.3.0 把落點從「收尾 fence 之後」（下一個按鍵就破壞 fence）改成「第一個內容行的
    開頭」，那是嚴格的改善；把 caret 放到**你點的地方**需要座標對映，本版**刻意**沒有
    納入範圍。所以這是一條畫出來的線，不是待修的缺陷 —— 但 40 行的 code block 上點
    第 38 行仍然會被丟到第 1 行，使用者應該知道。**本任務自己驅動量測**，同一個五行
    fenced block 的頂端 +6px、垂直中央、底部 −8px 三個落點：`selectionStart` 三次都是
    6，也就是第 2 行。

19. **`Alt+F10` 是否被真實瀏覽器或 OS 攔截，在本環境原理上不可驗**（Firefox 的 `F10`
    選單列、GNOME/KDE 的 `Alt+F10` 最大化）。**這一項沒有被驅動量測過，而且不可能在
    這裡被驅動量測** —— 需要使用者在真機確認。

## 三、未裁定的開放問題

20. **`ensureTableBurstOpen()` 只用 `startLine` 重新解析表格，而 Task 13 的姊妹路徑
    `handleTableCellFocusIn()` 用的是複合錨點，並且在自己的註解裡說 `startLine` 不夠。**
    （final review F9。**不修** —— Ruling T22-2。）

    **已被證明的**：兩者的實作確實不對稱（`ensureTableBurstOpen()` 的 `startLine` 單獨
    重解析 vs. `handleTableCellFocusIn()` 的 `data-block-id` 優先、`startLine` 後備、
    兩者都由 `tableIdentityOf()` 把關）；Task 13 的註解記了一個 `startLine` 單獨會失敗
    的量測形狀（表格前面的段落多長一行、區塊數不變）；`ensureTableBurstOpen()` 守的是
    會改資料的手勢（插入／刪除列欄、對齊、拖曳）。Ruling T13-2 處理的是這個函式的
    **另一個**問題（`[0]` 儲存格錨點，正確地維持原樣），T13-1 只要求 Task 13 為自己的
    修法量測候選；**是否回移，兩邊都沒有裁定過。**

    **沒有被證明的**：任何一次實際失敗。final review 的作者試著證偽而**做不到** ——
    驅動「表格上方的髒段落多長一行、然後按列 ＋ 泡泡」得到的是正確插入、沒有 banner，
    因為那次 render 並沒有讓表格脫離文件，復原分支根本沒被走到。本任務同樣**沒有**
    重現任何失敗，也沒有嘗試新的證偽路徑。

    所以這是一個「值得一條 v3.4.0 調查」的不對稱，**不是一個已知缺陷**。要把它變成
    缺陷，需要先找到一條真的會走進 `ensureTableBurstOpen()` 復原分支、而且
    `startLine` 在那裡名到別的東西的手勢。
