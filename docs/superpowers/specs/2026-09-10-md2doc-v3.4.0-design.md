## §1. TOC 與 slug 的雙重跳脫

### 量到的事實

輸入 `# Alpha & Beta` 與 `## C < D > E`，輸出：

```
TOC:     <a href="#alpha-amp-beta" title="Alpha &amp;amp; Beta">Alpha &amp;amp; Beta</a>
heading: <h1 id="alpha-amp-beta" ...>Alpha &amp; Beta</h1>
```

TOC 顯示成 `Alpha &amp; Beta`（雙重跳脫），slug 變成 `alpha-amp-beta`（實體名稱
`amp` 被當成文字併進錨點），`C < D > E` 的 slug 變成 `c-lt-d-gt-e`。

### 根因（量測，非推論）

`marked` 的 lexer 對同一個 heading 給出兩種跳脫狀態：

```
heading.text  = "Alpha & Beta <x> `a&b`"     ← 原始，未跳脫
  tok text     text= "Alpha &amp; Beta "     ← 已跳脫
  tok codespan text= "a&amp;b"               ← 已跳脫
```

而 `renderer.heading` 寫的是：

```js
const headingText = stripHtmlTags(flattenTokenText(token.tokens) || token.text || '');
```

`flattenTokenText()` 的葉節點回傳 `item.text`（已跳脫），`|| token.text` 的後備支
回傳原始字串。**同一個 `||` 的兩邊跳脫狀態不一致**——這是缺陷本身，不只是「多跳一次」。

三個消費者全部吃到已跳脫的字串：

1. `renderTocNodes()` 的 `escapeHtml(node.text)` → 雙重跳脫的 TOC 標籤與 `title`
2. `slugifyHeading(headingText)` → 錨點裡帶 `amp` / `lt` / `gt`
3. `startSection({ depth, id, text })` → section index（捲動同步、搜尋）拿到雙重跳脫的文字

### 修法

新增 `unescapeHtml(value)`，作為既有 `escapeHtml()` 的**精確逆函式**（處理
`&amp;` `&lt;` `&gt;` `&quot;` `&#39;`，且 `&amp;` 必須最後處理以免二次解碼）。
在 `flattenTokenText()` 的兩個葉節點分支（`item.type === 'codespan'` 與最後的
`return item.text || ''`）套用它，使該函式的契約變成
**「一律回傳純文字，永遠不帶 HTML 實體」**。`|| token.text` 的後備支因此與主支一致。

修在源頭一處，三個消費者一起好。`escapeHtml(node.text)` 與
`<h1 id="...">` 的 `headingHtml`（走 `parser.parseInline`，本來就正確）都不動。

### 裁定：接受 slug 改變（breaking）

`#alpha-amp-beta` → `#alpha-beta`，`#c-lt-d-gt-e` → `#c-d-e`。**外部指向舊錨點的
連結會斷。** 仍然要改：舊 slug 是缺陷的產物，留著等於把 bug 當成契約。
CHANGELOG 必須有一段 breaking 說明，並舉出實際的前後對照。

`slugCounts` 的去重計數器不受影響——它以修正後的 base 為鍵，行為不變。

### 測試

`test/md2doc.test.js` 增列（regex 對渲染後 HTML）：

- `# Alpha & Beta` → TOC 連結的 `title` 與內文皆為 `Alpha &amp; Beta`（**單層**跳脫），
  且 `href="#alpha-beta"`
- `## C < D > E` → `href="#c-d-e"`
- `` # A `x&y` B `` → codespan 的內容進 TOC 時同樣只跳脫一層
- `# A <b>c</b> D` → `stripHtmlTags` 仍然把標籤拿掉，slug 為 `a-c-d`
- 去重：兩個同名 heading 仍得到 `foo` 與 `foo-2`

## §2. 表格列拖曳之後畫面跳到表頭

### 症狀

用 ⠿ 把表格的某一列拖到別的位置，放開之後畫面捲到表格表頭。應該留在原本的捲動位置。

### 候選機制（**尚未驅動驗證**）

`performRowDrop()` 結尾：

```js
const activeIndex = (currentBurst && currentBurst.activeCellEl)
  ? tableCellsOf(liveTableEl).indexOf(currentBurst.activeCellEl) : -1;
...
restoreTableFocus(liveTableEl, activeIndex);
```

而 `restoreTableFocus()`：

```js
const cell = cells[cellIndex >= 0 ? Math.min(cellIndex, cells.length - 1) : 0];
if (!cell) return;
...
cell.focus();
placeCaretAtEnd(cell);
```

純拖曳手勢從未點進任何儲存格 → `currentBurst.activeCellEl` 為 null → `activeIndex`
為 `-1` → 落到 `cells[0]`（**第一個表頭儲存格**）→ `cell.focus()` → 瀏覽器把它捲進視野。

### Plan 的第一步必須是重現，不是修

這條是讀碼推出來的，**沒有驅動過**。plan 的第一個 step 是寫一支會紅的 runtime 測試：
記錄拖曳前的 `window.scrollY`，執行列拖曳，斷言 `scrollY` 不變且
`document.activeElement` 不是表頭儲存格。**若該測試在修改前就是綠的，代表機制猜錯，
停下來重新量，不要繼續。**

### 修法（在機制確認之後）

`activeIndex < 0` 時不呼叫 `restoreTableFocus()`。理由：這個手勢從頭到尾沒有焦點，
不該憑空製造一個。`activeIndex >= 0`（拖曳前確實在編輯某一格）的路徑不變——那時
把焦點還回同一格是正確的。

同一支測試要涵蓋兩邊：拖曳前有作用中儲存格時，焦點仍回到該格（不得回歸）。

### 姊妹路徑（已查證，不是推測）

`restoreTableFocus()` 全檔**只有兩個呼叫點**，而且兩個都是
`restoreTableFocus(liveTableEl, activeIndex);`：一個在 `performRowDrop()` 裡，
一個在 `performColDrop()` 裡。兩者的 `activeIndex` 算法逐字相同，所以**欄拖曳有完全一樣的缺陷**，一起修，
兩邊都要有測試。

而 `performBlockDrop()` 與 `performListItemDrop()` **完全不呼叫 `focus()`、
不呼叫 `scrollIntoView()`**。也就是說「拖曳手勢不製造焦點」已經是本專案在其他兩條
拖曳路徑上的既有慣例——這次的修法是讓表格拖曳**回到**那個慣例，不是發明新規則。

## §3. 儲存按鈕

### 現況

工具列（`lib/editor/toolbar-model.js`）目前沒有儲存按鈕。存檔只有 `Ctrl+S` 一條路
（`client.js` 的 `save()`，`(e.ctrlKey || e.metaKey) && !e.shiftKey && e.key === 's'`）。
髒狀態只表現在分頁標題的 ●。

使用者已明確表示：**不要自動存檔**，符合 office viewer 的操作習慣。這一版不改這一點。

### 設計

在 `toolbar-model.js` 新增群組 `file`，置於 `history` 群組之前（最左）：

```js
{ id: 'save', group: 'file', label: '💾', icon: '💾', title: '儲存 (Ctrl+S)', toggle: false },
```

行為：

1. **狀態接既有真相，不另造一套**。`client.js` 已有
   `const dirty = stack.dirtyDepth !== 0 || burstHasUncommittedEdit();`
   ——按鈕的 enabled/disabled 由同一個運算式決定，與標題 ● 同源。
2. 乾淨時 disabled 且視覺淡化；髒的時候亮起。**按鈕本身就是儲存狀態指示器。**
3. 點擊 → 與 `Ctrl+S` 走完全相同的 `save()`，不複製任何邏輯。
4. **必須把 caret 還回去。** backlog 第 6 項記錄 `quote` / `code` / `line` 按完會把
   caret 留在 BODY，鍵盤使用者出不來。新按鈕不准再生一個同類缺陷——按下之後
   caret 必須回到按之前的位置。這一條要有自己的測試。
5. 必須走得到 `Alt+F10` 鍵盤游標，且在 disabled 時游標會跳過它（v3.3.0 已有
   「游標所在按鈕被關掉就跳到下一顆」的機制，這裡沿用，不新寫）。
6. 存檔成功後按鈕變回 disabled；存檔失敗（既有的 banner 路徑）維持 enabled。

### 測試

- `test/toolbar-model.test.js`：`file` 群組存在、`save` 在最左、群組順序不變
- runtime：打字 → 按鈕亮 → 點擊 → 檔案落磁碟且按鈕變暗
- runtime：點擊後 caret 回到原位（§3 第 4 點）
- runtime：`Alt+F10` 走得到，且乾淨時游標不會停在它上面
- runtime：存檔失敗（伺服器回 409）時按鈕保持 enabled，banner 照常升起

## §4. drawio 內嵌

### 觸發語法

- `![alt](path.drawio)`
- `![alt](path.xml)` — **但 `.xml` 必須嗅探內容**，見下
- `#SheetName` 或 `#N`（1-based 頁碼）選擇初始顯示的頁：`![](x.drawio#Flow)`、`![](x.drawio#2)`

### `.xml` 的判別

副檔名不足以判斷。讀檔後檢查根元素是否為 `<mxfile>` 或 `<mxGraphModel>`：

- 是 → 當 drawio 處理
- 否 → **原樣走今天的路**（`inlineImageSrc` 的既有行為），不報錯、不改變現狀

`.drawio` 副檔名同樣要嗅探——一個副檔名對但內容壞掉的檔案應該得到明確錯誤，
而不是產生空白的 SVG。

### 渲染策略：照 graphviz，不是照 mermaid

md2doc 現有兩種圖表嵌入模式：

| | 引擎位置 | 產物 |
|---|---|---|
| mermaid | 用戶端（3.2 MB 內嵌進 HTML） | `<div class="mermaid">` + 執行期渲染 |
| graphviz | **Node 側建置時**（WASM，不進 HTML） | 內嵌 SVG |

drawio 走 **graphviz 這條**。兩個理由，都是量到的：

1. diagrams.net 的 `viewer-static.min.js` 是 **4.0 MB**。mermaid 已經佔 3.2 MB；
   再加 4 MB 會讓每一份引用 drawio 的 HTML 直接翻倍。
2. 那支 viewer 開頭就把 `STYLE_PATH` / `SHAPES_PATH` / `STENCIL_PATH` / `mxBasePath`
   預設指向 `https://viewer.diagrams.net/...`。**用 stencil 形狀的圖在離線時會破圖**,
   而 md2doc 的立身之本就是自帶一切的單檔 HTML（圖片都已 base64 內嵌）。
   建置時渲染把這個問題在 Node 側一次解決。

### 實作形狀

沿用 graphviz 的兩段式，**逐 part 烤**：

1. `renderer.image`（或其上游的圖片解析）辨識出 drawio 來源時，回傳佔位元素：
   `<div class="drawio" data-drawio-src="<base64 XML>" data-drawio-page="<name or index>"></div>`
   ——來源以 base64 攜帶，理由與 graphviz 相同（任意 XML 內容對屬性值不安全）。
2. 非同步 post-pass `bakeDrawio(part)`，與 `bakeGraphviz` 並列，在同一個
   `parts.map(...)` 之後執行。

`lib/md2doc.js` 現有註解已經寫明**為什麼必須逐 part 烤**：

> v3.2.0: bake EACH part, then join — not join-then-bake. The patch path inserts
> parts[i] straight into the DOM and the client has no graphviz renderer
> (`__md2docInitDiagrams` handles only mermaid and WaveDrom), so an unbaked part
> lands as an empty `<div class="graphviz">`.

drawio 完全相同：`__md2docInitDiagrams` 不會認得它，一個沒烤的 part 會變成空 div。

### 引擎怎麼跑

puppeteer 已是依賴（PDF 匯出在用）。`bakeDrawio()` 開一顆 headless page，載入
**本機**的 `viewer-static.min.js`（隨套件出貨，加入 `files`），把
`STYLE_PATH` / `SHAPES_PATH` / `STENCIL_PATH` / `mxBasePath` / `DRAW_MATH_URL` /
`GRAPH_IMAGE_PATH` 全部改寫成本機路徑，呼叫 `GraphViewer.createViewerForElement()`，
取出產生的 `<svg>`。

**一份文件共用一顆 browser instance**，不是每張圖開一顆。多張圖循序處理。

若 viewer 沒有產出 SVG（壞檔、不支援的形狀），產出一個帶錯誤訊息的可見佔位元素，
**不要**靜默產生空白——這是 v3.3.0 反覆學到的：靜默的失敗最貴。

### 多頁

**裁定：所有頁一次全部烤進去，用 CSS 切頁。**

產出 `<div class="drawio" data-drawio-pages="Architecture,Flow">` 內含 N 個
`<svg>`，只有選定那一頁沒有 `hidden`。於是：

- hover 頁籤列切頁 = 切 `hidden`，**完全不需要引擎**
- lightbox 換頁同理
- 離線完全可用
- PDF 匯出自動正確（PDF 是靜態的，只會印出選定那一頁——這是正確行為）

代價：多頁檔案的 HTML 會大一些（每頁一份 SVG）。可接受——SVG 是向量文字，
比 4 MB 的引擎小得多。

### lightbox

md2doc 已有圖表 lightbox（`test/lightbox.test.js`）。drawio 的 SVG 掛進既有機制。
**`CLAUDE.md` 的鐵則要遵守**：`.lightbox-canvas` 以 px 調整尺寸，
**不得**改用 `transform: scale()`（scroll extent 不會跟著變，放大後的邊緣點不到，
`test/lightbox.test.js` 有守）。

### 已知邊界（誠實寫進 CHANGELOG）

**靜態 SVG 沒有圖層切換。** fork 的 lightbox 可以切 drawio 圖層；這裡不行，
因為圖層資訊在烤成 SVG 時就被壓平了。這是選擇建置時渲染的代價，是畫出來的線，
不是待修的缺陷。

### `--edit` 模式

編輯器的 server 監看被引用的 `.drawio` / `.xml` 檔；檔案變更時重烤該 part 並推給
用戶端。**與 §5 的 wavedrom 編輯器無關**，兩者不共用機制。

### 測試

- `test/drawio.test.js`（新檔，加進 `package.json` 的 `test`）：
  - `![](x.drawio)` 產生內嵌 `<svg>`，且 HTML 中**不出現** `viewer-static`
  - 多頁檔案產生 N 個 `<svg>`，只有一個沒有 `hidden`
  - `#Flow` 與 `#2` 都選到第二頁
  - `![](notdrawio.xml)`（根元素不是 `mxfile`/`mxGraphModel`）行為與今天完全相同
  - 壞掉的 `.drawio` 產生可見的錯誤佔位元素，不是空白
  - 產物離線可開：HTML 中不含任何 `viewer.diagrams.net` 的 URL
- runtime：`--edit` 模式下 lightbox 開得起來、頁籤切得動

## §5. wavedrom GUI 波形編輯

### 目標

滑到已渲染的 wavedrom 圖上出現 Edit，點下去用滑鼠編輯波形：塗電位
（`0 1 x z p n h l u d =`）、增刪／複製貼上 cycle、lane 改名與重排、分組、
在 node 之間畫 `edge` 標註、設 head/foot/hscale。存檔寫回 code block 是**最小 patch**，
註解、縮排、引號風格都保留。

### 現況

md2doc 已經渲染 wavedrom（`lib/md2doc.js` 的 ` ```wavedrom ` → `<script type="WaveDrom">`，
引擎 pinned 在 `wavedrom@3.5.0`，理由寫在原始碼註解：3.6.1+ 的 `exports` map
不再暴露 `wavedrom/wavedrom.min.js` 與 `wavedrom/skins/default.js`）。
**這一版不動渲染，只加編輯。**

### 分層（四個新檔，與現有 `lib/editor/*.js` 同層）

| 檔案 | 職責 | 依賴 | 測試方式 |
|---|---|---|---|
| `lib/editor/wave-codec.js` | 解析 WaveJSON、序列化、最小 patch 寫回、文件層 ops | 無 | 純函式 |
| `lib/editor/wave-geometry.js` | 座標計算與 hit testing | 無 | 純函式 |
| `lib/editor/wave-store.js` | 文件狀態、undo/redo、與 burst/history 對接 | codec | 純函式 + runtime |
| `lib/editor/wave-ui.js` | 手繪 SVG 畫面、工具列、lane 清單、edge 檢視 | 全部 | puppeteer |

分層的理由：`blockmap.js` / `lineops.js` / `patchmap.js` / `selection.js` /
`inline-md.js` / `toolbar-model.js` 已經是這個模式——**純邏輯抽成可用純函式測試的檔案，
只有真正碰 DOM 的部分需要 puppeteer**。v3.3.0 的經驗是 puppeteer 測試一支要跑 20 分鐘，
能移到純函式層的每一條斷言都是直接的時間節省。

### `wave-codec.js` 的關鍵約束

**WaveJSON 不是嚴格 JSON，是 JS 物件字面值。** 鍵不加引號、允許尾逗號、允許註解、
單引號字串都是常見寫法。真實世界的 wavedrom code block 幾乎都長這樣：

```
{ signal: [
  { name: "clk",  wave: "p......" },   // 主時脈
  { name: "data", wave: "x.34.5x", data: ["a","b","c"] },
]}
```

因此：

1. **解析不得用 `JSON.parse`。** 需要一個容忍上述形狀的小型解析器，且必須為每個
   值記錄它在原始字串中的**位元組區間**——最小 patch 寫回靠這個。
2. **序列化只在不得已時使用。** 正常路徑是 `patchSource(parsed, edits)`：只改動需要
   改的那幾段位元組，其餘原樣保留。註解、縮排、引號風格因此自然存活。
3. 真的無法只做局部替換時（例如整個 `signal` 陣列重排），才退回整段重寫，**而且要
   讓使用者知道它動了哪一段再等確認**——不得靜默重排使用者的檔案。

`wave` 字串的 `.` 是「延續前一個字元」。codec 對外提供 `expandWave()` /
`collapseWave()` 一對，UI 一律操作展開後的陣列，寫回前才收合。

### 進入與退出

- **進入**：滑鼠移到已渲染的 wavedrom 圖上 → 浮出 Edit 按鈕 → 點擊開啟編輯器。
- **裁定：overlay 掛在 `document.body`，不掛在 block 裡。** 塞進 `.content` 內的 DOM
  會被序列化進 markdown——這是 md2doc 編輯器既有的硬約束（fork 因為 vditor 有完全
  相同的約束，這一點兩邊一致）。
- **退出**：Escape 或關閉按鈕。**Escape 的語意必須與 v3.3.0 的其餘部分一致**：
  丟棄，但可以用 `Ctrl+Z` 取回（v3.3.0 的「停放」機制）。不得產生一個「丟了就沒了」
  的新入口——backlog 第 5 項正是這個症狀還沒收乾淨的地方。

### 寫回

**裁定：走既有的 burst / history。** 編輯器的每一次動作 `snap()` 一次；關閉時把
最小 patch 套進 code block 的來源行。於是：

- `Ctrl+Z` 救得回來
- 只有 `Ctrl+S` 才落磁碟（與整個編輯器一致，也符合使用者「不要自動存檔」的要求）
- 標題的 ● 與 §3 的儲存按鈕自動反映

**不得**繞過 burst 直接寫 `lines`。

### 渲染與互動的分工

**裁定：編輯層自己畫 SVG，預覽用真正的 WaveDrom 引擎。**

理由（fork 的 CONTRACT.md 記錄了同一個發現，而它在 md2doc 同樣成立）：官方引擎
輸出的 DOM 沒有穩定契約，不能當互動基質。因此：

- 編輯畫面是我們自己畫的 SVG，`wave-geometry.js` 負責座標與 hit testing
- 旁邊同時掛一份真正的 WaveDrom 渲染結果作為視覺真相
- 兩者由同一份文件狀態驅動

### 鍵盤

v3.3.0 的教訓（backlog 第 6、7、9、10 項）是：**每一個新的互動面都要在設計時就想
鍵盤，不能事後補。** 這一版的 wavedrom 編輯器必須：

- 可用鍵盤在 cycle / lane 之間移動
- 可用鍵盤塗電位
- Escape 逐層退出（先關子面板，再關編輯器），與 v3.3.0 的 `H▾` 選單同款
- 焦點離開編輯器時不得把 caret 丟在 BODY

### 測試

- `test/wave-codec.test.js`（純函式）：
  - 不加引號的鍵、尾逗號、行內註解、單引號字串都解析得出來
  - `expandWave` / `collapseWave` 對所有合法字元往返一致
  - `patchSource` 只改動目標區間：改一個 cycle 之後，**其餘位元組逐字不變**
    （包含註解與縮排）
  - 無法局部替換時回報「動了哪一段」，而不是靜默重寫
  - 壞掉的來源回傳帶 offset 的錯誤，不丟例外給呼叫端
- `test/wave-geometry.test.js`（純函式）：座標 ↔ (lane, cycle) 往返、邊界落點
- runtime / journey：進入、塗電位、增刪 cycle、lane 重排、edge 標註、Escape 可
  `Ctrl+Z` 取回、寫回是最小 patch、`Ctrl+S` 才落磁碟、鍵盤全程可用

## §9. 交付順序與風險

### 分批

| 批 | 內容 | 停在這裡可發嗎 |
|---|---|---|
| 1 | §1 TOC/slug、§2 列拖曳、§3 儲存按鈕、§6 的 13 項 | 可 |

每一批結束都是一個完整、測試全綠、可以發版的狀態。**若中途要停，停在批次邊界。**

### 誠實的規模評估

這一版**比 v3.3.0 大**。v3.3.0 是 20 個 task、50 個 commit、跨多個 session，而它
沒有任何一個項目的量體接近 §5。使用者已知此事並選擇「全部一版」。

### 已知會咬人的地方

1. **`test/editor-client-runtime.test.js` 與 `test/editor-journey.test.js` 各要跑
   20–25 分鐘。** v3.3.0 的做法是實作者**不跑這兩支**（會在等待時被 API timeout
   打斷），回報 NEEDS_RUN 由控制端跑完餵回。plan 必須帶著這條規則。
2. **跑那兩支時絕不 pipe**（`| tail` 之類）——exit code 會變成 pipeline 尾端的，
   紅的會被回報成綠的。直接讀 output file。
3. **間歇性紅不等於 flake。** v3.3.0 收尾時有一列在同一顆 commit 上三跑兩綠一紅，
   查下去是測試 harness 把「response headers 到了」當成「render 套用完了」。
   帶 AssertionError 的紅一律要查到機制，不准以「重跑就綠」結案。只有不帶
   AssertionError 的基礎設施 flake（`ProtocolError: Runtime.callFunctionOn timed out`、
   `net::ERR_NETWORK_CHANGED`）適用重跑規則。
4. **一律用引文錨點定位，不要用行號。** 行號會漂移。
5. **`docs/superpowers/` 與 `.superpowers/` 永遠不 `git add`。**
